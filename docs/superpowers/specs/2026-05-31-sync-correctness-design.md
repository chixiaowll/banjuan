# 同步正确性设计(mtime 保留 / 删除传播 / 冲突处理)

日期:2026-05-31
状态:设计待评审
关联:[LAN 直连同步 Plan 1](../plans/2026-05-31-lan-direct-sync-plan1-engine.md)、未来 CRDT 多端同步(memory: project_sync_requirement)

## 背景

`SyncService` 当前以**文件 mtime** 为唯一判据做 last-write-wins(±1000ms 宽限),删除靠 `.banjuan/sync-snapshot.json` 快照传播。LAN 直连同步落地后,实测暴露三个正确性问题:

1. **无限全量抖动**:下载后本地文件 mtime = 下载时刻,比源新 → 下次回传;回传后远端 mtime 又变新 → 再下载。同一批文件无限来回。
2. **冲突会静默覆盖**:两端都改同一文件时,mtime 新的赢,旧的那份**无备份地被覆盖**。
3. **删 vs 改**:一端删文件、另一端改同一文件,当前"删除赢",改动丢失。

本设计在**不破坏现有 WebDAV 同步、不动移动端**的前提下,系统性地修正这三类问题。真正的字段级自动合并(CRDT)是远期独立计划,不在此范围。

## 数据存储粒度(决定冲突频率)

| 数据 | 存储 | 冲突面 |
|---|---|---|
| 标注 annotations | 每条一个文件 `.banjuan/data/annotations/<prefix>/<id>.json` | 极低 |
| 文档元数据 documents | 每条一个文件 `.banjuan/data/documents/<prefix>/<id>.json` | 极低 |
| 笔记 notes | 每篇一个文件 `.banjuan/notes/<uuid>.json` | 低 |
| 标签 tags | **单文件** `.banjuan/tags.json` | 高 |
| 原始 PDF/EPUB | 单文件,近乎只读 | 极低 |

**关键护城河**:绝大多数内容是"每条一个文件"。两端**新增不同的**标注/笔记 = 不同文件 = 不冲突,自动各自传播合并。真正的整文件冲突只发生在:**同一条**笔记/标注/文档在两端都被改,或**单文件 `tags.json`** 两端都动过。

## 设计

### 块 1:传输保留 mtime(消除假冲突)

标准同步语义(rsync -t / Syncthing / Dropbox):**同步副本继承源文件的 mtime**。直接设置**文件本身的 mtime**(`stat().mtimeMs`),不另存第二份记录——因为比较器读的就是文件 mtime,单一真相最不易漂移。

1. **`PlatformFS` 新增可选方法 `setMtime?(path, mtimeMs)`**。
   - Node 实现:`fs.utimes`。
   - 移动端(capacitor)**不实现**(接口可选)→ 零改动、零影响。
   - 所有调用处用 `await fs.setMtime?.(...)` 且包 `try/catch` → 不支持就**退回现状行为**,绝不报错。
2. **下载后**:`SyncService` 把本地文件 mtime 设为 `remote.mtime`(列表已带),**仅当 `remote.mtime > 0`**(服务器没给 Last-Modified 时跳过 → 永不比现状更差)。此项对现有 WebDAV 同步同样减少抖动,纯收益。
3. **上传到 LAN host**:client 在 PUT 带自定义头 `X-Banjuan-Mtime: <ms>`;LAN host 写文件后按它 `setMtime`。
   - `SyncAdapter.upload` 增加**可选** `mtimeMs` 参数;只有传了才发头。
   - 通用 WebDAV 服务器忽略未知头(no-op);仅自有 LAN host 认它。用自定义头名(非 `X-OC-Mtime`)避免误触发网盘特殊行为。

**为何靠现成 1 秒宽限就收敛**:LAN host 的 PROPFIND 用 RFC1123 时间(**秒精度**),而设 mtime 是毫秒。但比较本就有 ±1000ms 宽限,正好吸收"秒截断"。两端 mtime 设一致后,下次 diff < 1s → 跳过。**不需要改比较逻辑**。

### 块 2:快照升级为基线(支持"双改"检测)

当前 `sync-snapshot.json` 只存**文件名清单**(够做删除传播,不够做冲突检测)。升级为记录**每个文件上次同步后的 mtime**:

```jsonc
// .banjuan/sync-snapshot.json （每台设备本地、不参与同步)
{
  "version": 2,
  "timestamp": 1748600000000,
  "files": { "Books/a.pdf": 1748500000000, ".banjuan/notes/x.json": 1748500001000 }
}
```

- **向后兼容**:遇到旧格式(`files` 为字符串数组)按"只有文件名、无 mtime 基线"处理 → 退化为当前行为(只传播删除、不做双改检测),下次写新格式。
- 基线 mtime 在块 1 收敛后两端相同(client 记本地值,等于 host 值),所以"远端是否改过 = `|remote.mtime − baseline| > 宽限`"成立。

### 块 3:全情况行为表

设 `base` = 该文件在快照基线里的 mtime(无则视为"不在基线")。"changed" = 当前 mtime 与 base 相差 > 1000ms。

| 本地 | 远端 | 在基线 | 含义 | 动作 |
|---|---|---|---|---|
| 有 | 有 | — | 仅一端 changed | 把 changed 那端同步到另一端(mtime 保留) |
| 有 | 有 | 在 | **两端都 changed 且彼此不同** | **真冲突** → 见下方冲突处理 |
| 有 | 有 | — | 都没 changed(mtime 一致) | 跳过 |
| 有 | 无 | 在,且本地**未** changed | 远端删除 | **本地删** |
| 有 | 无 | 在,且本地**已** changed | **删 vs 改** | **不删**,把本地当"新增"上传回远端(改动胜过删除,不丢) |
| 有 | 无 | 不在 | 本地新增 | 上传 |
| 无 | 有 | 在,且远端**未** changed | 本地删除 | **远端删** |
| 无 | 有 | 在,且远端**已** changed | **改 vs 删** | **不删**,把远端当"新增"下载到本地(不丢) |
| 无 | 有 | 不在 | 远端新增 | 下载 |

**保命兜底(保留现有逻辑)**:若远端整体为空但快照非空 → 关闭删除判定,当作"远端未就绪",避免一次性删光。

### 块 4:冲突的具体处理与用户解决方式

**永不静默删除/覆盖**;冲突 = 多出一个**看得见、可操作**的副本,用现成的列表 + 删除收尾。

- **笔记 / 标注 / 文档(每条一文件)**:不覆盖,把对方那份**另存为一个新条目**,标题/角标标 "**(冲突副本)**"。用户在现有列表里看到两份,打开对比,删掉不要的。复用现有查看/删除 UI,无需专门冲突界面。
- **标签 `tags.json`(单文件)**:**自动合并(并集)**——标签集合两端各加几个,正确结果就是并集,不打扰用户。仅"同一标签两端改成不同名"这种极少数退化为保留两者让用户删。
- **原始 PDF/EPUB**:对方版另存为 `原名(冲突副本-设备-时间).ext`,在文档列表可见,用户删掉多余的。
- **同步小结**:沿用现有同步结果提示,追加 "本次产生 N 个冲突副本",引导用户去清理。

冲突副本命名含**设备标识 + 时间戳**,避免二次同步再冲突。

## 安全保证(对应"不会出问题")

- `setMtime` 可选 + best-effort → 移动端零改动,任何平台不支持也不崩。
- 下载保留 mtime 有 `>0` 守卫 → 永不比现状差。
- 上传 mtime 走自定义可选头 → 真实 WebDAV 视为 no-op,不受影响。
- 快照新格式向后兼容旧格式 → 升级无缝。
- 冲突一律"留两份",**绝不静默丢数据**;远端空时**不触发批量删除**。
- 不改 mtime 比较器本身,靠现成 1 秒宽限收敛。

## 不在本设计范围(YAGNI / 远期)

- **多端(3+ 设备)**:当前单份快照对两台稳妥;轮流跟多台 host 同步会混用快照,留待多端方案。
- **字段级自动合并**:同一条笔记/标注两端都改仍产生冲突副本;真正的自动合并是 CRDT(cr-sqlite)独立计划。
- **实时/后台自动同步**:沿用手动触发。

## 测试策略

- **收敛(最硬指标)**:集成测试"连续同步两次"——host-only 文件第一次 `downloaded≥1`、第二次 `0/0`;client-only 文件第一次 `uploaded≥1`、第二次 `0/0`。
- **删除传播**:同步后在一端删文件,再同步 → 另一端该文件消失;反向亦然。
- **删 vs 改**:一端删、另一端改同一文件,同步后**改动保留**(未被删)。
- **双改冲突**:两端改同一笔记 → 产生一个"(冲突副本)"条目,原件不丢。
- **标签并集**:两端各加不同标签 → 同步后两边都有全部标签。
- **mtime 头**:handler 单测——PUT 带 `X-Banjuan-Mtime` 后文件 mtime 被正确设置。
- 现有 14 + LAN 既有测试继续保证旧行为不破。
